# Research Summit

Internal research dashboard portal for the Summit team.

## Tech stack

- **Vanilla JavaScript** (ES modules, no framework, no build step)
- **Supabase** for auth (magic-link OTP) and database (PostgreSQL)
- **Netlify** for hosting (auto-deploys from GitHub)
- **CSS** — custom, no framework. Design uses Inter font, navy/steel palette.
- **Chart.js** (v4.4.1) loaded from CDN for charts and scatter plots

## Project structure

```
index.html              — App shell (sidebar + tab panels, loaded after auth)
login.html              — Login page (magic-link OTP flow)
js/auth.js              — Authentication, role checking, session management
js/supabase-client.js   — Single Supabase client instance
js/nav.js               — Sidebar navigation and tab switching
js/portal-data.js       — All data arrays (stocks, investors, companies, images)
js/companies.js         — Companies tab (grid, detail view, four-pillar analysis)
js/market-analysis.js   — Market Analysis tab (sector bars, filters, scatter, tables)
js/hedge-funds.js       — Hedge Funds tab (alpha chart, benchmark, investor cards)
css/base.css            — CSS variables and reset
css/layout.css          — Loading overlay styles
css/portal.css          — Sidebar, topbar, cards, tables, charts, all portal UI
sql/schema.sql          — Database schema (run in Supabase SQL Editor)
netlify.toml            — Netlify build + routing config
env.js                  — Local dev credentials (gitignored, generated by Netlify at build)
```

## Conventions

- All JS uses ES module imports (`import/export`), loaded via `<script type="module">`
- Supabase SDK loaded from CDN: `https://cdn.jsdelivr.net/npm/@supabase/supabase-js@2/+esm`
- No npm/node dependencies for the frontend — everything runs as a static site
- Each dashboard tab is a `<div class="tp" id="tp-{tab}">` inside `index.html`
- Page data loaders are registered in `index.html` via `registerPageLoader(name, loaderFn)`
- Navigation items are `.ntb.nav-item[data-page][data-tab]` buttons in the sidebar
- Tab IDs map: companies→co, market-analysis→rot, hedge-funds→inv (defined in js/nav.js)
- Role access is controlled in `js/auth.js` ROLE_CONFIG — add new roles there
- CSS variables are defined in `css/base.css` (:root)

## Adding a new dashboard page

1. Add a new `<div class="tp" id="tp-{tab}">` in `index.html`
2. Add a `.ntb.nav-item[data-page="{name}"][data-tab="{tab}"]` button in the sidebar nav
3. Create `js/{name}.js` with an exported `load{Name}Page()` function
4. Register it in `index.html`: `registerPageLoader('{name}', load{Name}Page)`
5. Add the tab→page mapping in `js/nav.js` TAB_MAP and TAB_TITLES
6. Add the page name to the appropriate role's `allowedPages` in `js/auth.js`

## Adding a new team member

1. Insert their email into `user_roles` in Supabase: `insert into user_roles (email, role) values ('email', 'role_name')`
2. Add their role to ROLE_CONFIG in `js/auth.js` if it's a new role
3. They sign in with their email — Supabase sends a magic-link code

## Environment

- `env.js` is gitignored. For local dev, edit it with your Supabase project URL and anon key.
- On Netlify, set `SUPABASE_URL` and `SUPABASE_ANON_KEY` as environment variables — the build command generates `env.js` automatically.

## Git workflow

**`main` is production — never push to it directly. All changes go through branches and pull requests.**

### For Claude (automated — follow these steps exactly)

Before making ANY code changes, Claude MUST:

1. **Check current branch:** run `git branch --show-current`
   - If on `main`: create a new branch before making changes
   - If on an existing feature branch: continue working on it
2. **Create a branch** (if needed):
   ```
   git checkout main && git pull origin main && git checkout -b <prefix>/<short-description>
   ```
3. **Branch prefixes:** `feat/` (new feature), `fix/` (bug fix), `chore/` (cleanup, config, docs)
4. **Make changes**, commit with clear messages
5. **Push the branch:** `git push -u origin <branch-name>`
6. **Open a PR** using `gh pr create` — include a clear summary of what changed and why
7. **Never merge the PR** — leave it for a team member to review and approve
8. **If the user asks to work on something new**, go back to step 1 (new branch from main)

### For team members

Most team members are non-technical. Claude handles all git operations for them. Team members just need to:

- **Describe what they want** — Claude creates the branch, writes code, and opens the PR
- **Review PRs on GitHub** — look at the changes, approve or request changes
- **Never edit files on `main` directly** — always ask Claude to make changes

### Branch rules

- One branch per feature/task — don't mix unrelated changes
- Keep branches short-lived — merge or close within a few days
- If two people are working on related things, coordinate to avoid editing the same files
- After a PR is merged, Netlify auto-deploys to production

### Resolving conflicts

If a PR has merge conflicts:
1. Pull latest main into the branch: `git pull origin main`
2. Resolve conflicts in the affected files
3. Commit and push — the PR updates automatically

## Do not

- Add npm dependencies or a build step — this is a zero-build static site
- Commit `env.js` or any file containing credentials
- Remove or weaken Row Level Security policies
- Change the auth flow without discussing with San first
